# Cloud解析 Free / 精密解析 profile比較（Issue #20）

2026-09-25〜26に、Issue #19のstaging Cloudflare Worker + Containerで、同じYaneuraOu + Suisho11 Plus（private image、build `faae69bfa42245ea9820cdf0b3420d95`、git `c6d5b52`）を使い、探索条件ごとの品質・時間・推定コストを実測した。**このレポートは判断材料であり、製品profileはまだ決めていない。** ユーザーが承認した値だけを後続Issue（#21以降）へ渡す。

全条件の集計表は[`cloud/bench/results/issue-20/aggregate.md`](../cloud/bench/results/issue-20/aggregate.md)、機械可読版は同じディレクトリの`aggregate.json.xz`に置いた。測定手順と再実行コマンドは[`cloud/README.md`](../cloud/README.md#issue-20-benchmark-mode)にある。

## 何を測ったか

- **局面**：CSA WCSC36の実戦棋譜20局から、序盤・中盤・終盤を各20局面、計60局面（重複なし）を抽出した。
  - 同じ大会の92手の1局を、棋譜1局の解析時間の測定に使った。
  - 抽出とhash固定の方法、出典の表記は[`cloud/bench/dataset/README.md`](../cloud/bench/dataset/README.md)にある。
  - dataset manifestのSHA-256は`ff5d15f9…affaad2`。
- **比較した条件（48条件）**：
  - Container：standard-2（1 vCPU / 6 GiB）とstandard-3（2 vCPU / 8 GiB）
  - Threads：1 / 2
  - 探索時間：100 / 250 / 500 / 1000 / 2000 / 5000ms
  - MultiPV：2 / 3
  - Hashは64 MiBで固定。各条件の定義は`cloud/bench/conditions.json`にある。
- **基準解析**：standard-3 / Threads 2 / 10000ms / MultiPV 3を、各局面で3回実行した。
  - 1回目を主基準、2・3回目を比較用の副基準とした。
  - 基準解析は「正解」ではない。より深く読んだ解析との差を測るための物差しとして扱う。
- **要求数**：1次測定（48条件×60局面＋基準解析180回）が3060件。候補4条件の追加2回が480件、1局解析が1104件、cold startが6件で、**合計4650件**（計画の上限は約5000件）。
- **instanceの確認**：各測定の前に、Container内の`osCpuCount`、CPU affinity、`/proc/meminfo`のMemTotal、build IDを確かめた。
  - standard-2は1 CPU / 6.49 GB、standard-3は2 CPU / 8.59 GBだった。
  - どの応答も、期待したinstanceとimageから返っていた。
- **失敗**：4650件中1件だけ失敗した（standard-3 / Threads 1 / 250ms / MultiPV 3）。
  - Workerが「Analysis container is unavailable」の502を返した一時的な失敗で、直後の要求は同じinstanceで成功している。
  - 失敗した試行も分母に残している。

1. **100 / 250msは、今のdriverでは使えない。**
   - 67〜88%がincompleteになった。これは測定の失敗ではない。
   - driverは、最終深さでMultiPVの全候補が正確な評価値付きで揃ったときだけ結果を採用する。短い時間ではその条件を満たす前に探索が終わる。
   - 500msでもincompleteが7〜18%残る。1000ms以上ならほぼ0%。
   - 短い時間を製品で使うなら、採用規則（一つ前の完了深さを使う、上限・下限付きの評価値を許す、など）を先に見直す必要がある。
2. **どの条件でも約0.8秒の固定時間がかかる。**
   - 今の経路は解析1回ごとにengineを起動し、評価関数を読み込み直している。
   - そのため、engineプロセスの経過時間は探索時間より約0.8秒長く、HTTP時間はさらに約0.2秒長い。例えば1000msの条件は、実際には約2.0秒かかる。
   - engineを常駐させれば、Freeの待ち時間とコストは大きく下がる見込みだが、今回は測っていない。
3. **2 vCPUが効くのはThreads 2のときだけ。**
   - NPSはstandard-2の各条件とstandard-3 / Threads 1がいずれも約39〜50万で、standard-3 / Threads 2だけが約81〜92万（約2倍）だった。
   - standard-2でThreads 2にしても速くならない。
4. **最善手の一致率（Top-1）では条件の差がほとんど出ない。**
   - 500ms以上のどの条件も47〜61%で横ばいだった。基準解析同士（1回目と2・3回目）でも65.8%しか一致しない。
   - 実戦の局面には評価の近い手が多く、Threads 2の探索は実行ごとに結果が揺れるためである。
   - 条件の差ははっきり出るのは、CP差のp90とTop-3包含率である。
   - 序盤のTop-1一致率は、どの条件でも35〜50%と低い。一方で序盤のCP差p90は約50と小さく、評価の近い手の間で入れ替わっているだけである。
5. **同じ局面をもう一度解析したとき、Threads 1は結果がほぼ変わらず、Threads 2は変わりやすい。**
   - Threads 1（standard-2）は、繰り返しでTop-1が85〜93%一致し、CP差の中央値は0だった。
   - Threads 2（standard-3）は、Top-1の一致が58〜64%、CP差の中央値は24〜30だった。
   - 精密解析で再解析すると結果が変わることがある。画面でどう見せるかを検討する必要がある。

## コスト

Cloudflareの公開料率（2026-09-25確認）から計算したgross額で、無料枠を引く前の値である。請求額の予測ではない。

- 料率：CPUは実際に使った分だけで $0.000020 / vCPU秒。メモリは確保した分で $0.0000025 / GiB秒、ディスクは確保した分で $0.00000007 / GB秒。
  - 出典：[Containers](https://developers.cloudflare.com/containers/platform/pricing/)、[Workers](https://developers.cloudflare.com/workers/platform/pricing/)、[Durable Objects](https://developers.cloudflare.com/durable-objects/platform/pricing/)
- **1局面あたり**：engineプロセスのCPU秒の中央値×CPU料率に、engineプロセスの経過時間×メモリ・ディスク料率を足した。
  - 要求と要求の間の時間、Worker・Durable Objectの料金、転送料は含まない。これらは合わせて1局面あたり$0.00001未満である。
- **1局あたり**：上の1局面の値×92手で計算した。
- **idle時間**：最後の要求の後、Containerは`sleepAfter = 5m`の間起きたままになる。
  - その間のメモリ・ディスク料金は、standard-2で約$0.0048、standard-3で約$0.0063。
  - 利用者が一人ずつ時々使う場合は、これが1回あたりのコストの大部分を占める。同時に使う人が多いほど、1人あたりの負担は小さくなる。
- **今回の測定全体**：Container CPUが$0.37〜0.50（engineのCPUを下限、確保したvCPU×稼働区間を上限とした）、メモリが$0.28、ディスクが$0.02、WorkerとDurable Objectが$0.03。合計は約$0.70〜0.83で、pilotの測定分は含まない。

## 計画から変えたこと

- **型ごとに専用のContainer appを使った。**
  - 最初は、一つのappの`instance_type`を区間ごとに切り替える計画だった。しかし切り替えても既存のVMが新しい型にならず、runtimeが設定と一致しなかった。
  - そのため、standard-2用とstandard-3用のbenchmark専用class / appを固定で用意した。
  - 通常のAPIは、従来どおりstandard-2のsingletonを使う。
- **cold startは「新しいinstanceの初回起動」として測った。**
  - 未使用のtarget名へ最初に送った要求で測定した。
  - `sleepAfter`でidleになった後の復帰は、今回の観測中に起きなかったため確認できていない。
- **cold startの条件を100msから候補条件に変えた。**
  - 100msではほとんどがincompleteになり、最初の成功までの時間が取れないため。
  - standard-2はFree初期候補、standard-3は精密解析初期候補で測った。
- **standard-3の1次測定は時間上限で一度止まった。**
  - manifestの90分の上限で1522件目の後に止まり、残りの98件を同じmanifestで再開した。
  - 再開後は別のinstanceで測っている。
- **候補の再測定と1局解析は、standard-2とstandard-3を並行して実行した。**
  - 型ごとに別のappで動くので、CPUを取り合わない。
- **deployを分けた。**
  - 測定対象の一覧（`ANALYSIS_BENCHMARK_TARGETS`）がWorker変数の上限5.1 kBを超えたため、再測定・1局解析と、cold startとで別々にdeployした。

## まだ分かっていないこと・制約

- 基準解析は正解ではない。棋力や、人が見て役に立つかどうかは測っていない。
- 1局の解析時間は、92手の1局を1本ずつ直列に解析した値である。並列化、同時に複数の要求が来た場合、キュー待ちは測っていない。
- idle状態からの復帰時間と、engineを常駐させた場合の時間は測っていない。
- Hashは64 MiBの1条件だけ。MultiPV 1、Threads 3以上、standard-4は比較していない。
- 測定はstaging環境での値である。production、アプリへの組み込み、課金画面はこのIssueの範囲外である。
- 測定のraw JSONLは、staging Workerのホスト名が改ざん検知用のfingerprintに含まれているため、公開リポジトリには入れていない。ローカルに保管している。`aggregate.md`と`aggregate.json.xz`はこのrawから作った集計である。
